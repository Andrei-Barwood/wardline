WARDLINE — PROMPTS DE IMPLEMENTACIÓN
Campaña educativa de defensa local, en cinco capítulos
Archivo de prompts para un agente de coding. No es el proyecto.

Cómo usar este archivo
----------------------
Entrega los prompts a un agente de coding, de uno en uno, en el orden 01 a 28.
No los paralelices: cada prompt modifica el mismo árbol y asume el anterior.
El agente debe dejar el repositorio instalable y los tests de ese prompt en verde
antes de pasar al siguiente.

Nombre del proyecto: Wardline.
Metáfora original: una ciudad desértica ficticia, Halcyon, cuyos servicios
públicos se defienden bajo presión. Cinco capítulos. Ningún personaje, nombre
comercial, diálogo, asset ni código de un videojuego existente.

Idioma del código, identificadores, errores estables y docstrings: inglés.
Idioma de README, docs de alumno, misiones y mensajes de este archivo: español.

Resultado esperado al terminar el prompt 28:
un repositorio clonable que arranca solo en localhost con

    ./scripts/setup.sh
    ./scripts/run.sh

y se comprueba con

    ./scripts/test.sh

Producto
- Distribución Python con layout src: paquete importable "wardline".
- Python >= 3.12.
- Procesos de escucha únicamente en 127.0.0.1, localhost o ::1.
- Si una dirección de escucha no es de loopback, el proceso rechaza arrancar.
- Datos de desarrollo en SQLite (./data/wardline.db). Toda SQL vive en
  wardline.storage. El resto del código habla con protocolos, para poder
  sustituir SQLite después sin reescribir la API.
- Secretos: no hay secretos reales. Las únicas claves son ficticias, solo para
  el laboratorio local, y aparecen únicamente en .env.example y en tests:

      viewer:dev-viewer-key
      operator:dev-operator-key
      admin:dev-admin-key

  Variable: WARDLINE_DEV_API_KEYS
  Formato: role:key separados por comas.
  Comparación en tiempo constante (hmac.compare_digest) sobre el digest
  SHA-256 de la clave presentada y el digest de la clave configurada.
  Nunca registres la clave ni el digest. En logs y respuestas, redacta.
- .env está en .gitignore. .env.example sí se versiona y solo contiene esas
  claves obviamente falsas, más hosts de loopback y puertos locales.

Enumeraciones y modelos (src/wardline/contracts.py). Congelados.

    class Role(StrEnum): VIEWER = "viewer"; OPERATOR = "operator"; ADMIN = "admin"

    class Severity(StrEnum):
        INFO = "INFO"
        LOW = "LOW"
        MEDIUM = "MEDIUM"
        HIGH = "HIGH"
        CRITICAL = "CRITICAL"

    Orden de severidad, de menor a mayor:
        INFO < LOW < MEDIUM < HIGH < CRITICAL

    class IncidentState(StrEnum):
        DETECTED = "DETECTED"
        INVESTIGATING = "INVESTIGATING"
        CONTAINED = "CONTAINED"
        RECOVERING = "RECOVERING"
        RESOLVED = "RESOLVED"

    class ServiceName(StrEnum):

        TCP = "tcp"
        UDP = "udp"
        AUTH = "auth"
        SIMULATION = "simulation"

        MONITORING = "monitoring"

    class ErrorCode(StrEnum):

        message_too_large = "message_too_large"

    class SecurityEvent (pydantic, frozen):
        timestamp: datetime          # timezone-aware UTC
        source: str                  # client_id o "system"

    class Principal:
        client_id: str
        role: Role
        authenticated: bool

        def now(self) -> datetime: ...

    class SystemClock: usa datetime.now(timezone.utc)

        def authenticate(self, token: str | None) -> Principal | None: ...

    Identidad de cliente:
        client_id coincide con ^[a-z0-9][a-z0-9-]{0,63}$
        Rechaza cualquier otro valor con invalid_message.
        El servidor asigna session_id uuid4 en TCP. No lo elige el cliente.

Hosts http_host, tcp_host y udp_host solo pueden ser 127.0.0.1, localhost o ::1.
Puertos en 1024..65535. Nada de puertos privilegiados.
database_url de desarrollo debe ser sqlite. Rechaza esquemas postgres, mysql,
http, https. El punto de sustitución futuro es el protocolo Storage, no esta
variable en el laboratorio.

Un patch de configuración de administrador solo puede tocar esta lista blanca:

    tcp_max_connections
    tcp_read_timeout_seconds
    tcp_idle_timeout_seconds
    tcp_max_message_bytes
    udp_max_datagram_bytes
    udp_packets_per_second
    rate_limit_requests_per_minute
    rate_limit_burst
    log_level

Cualquier otra clave, incluidos hosts, puertos, database_url y dev_api_keys,
se rechaza con validation_error. Los topes de rango de arriba se aplican también
al patch. No se puede usar el patch para aflojar un control más allá del rango.

Formas JSON congeladas.

GET /health -> 200 si todos los críticos están "ok"; 503 si alguno está "down".
Nunca incluye claves.

    {"status": "ok" | "degraded",
     "checks": {"http": "ok"|"down", "tcp": "ok"|"down",
                "udp": "ok"|"down", "database": "ok"|"down"}}

"degraded" acompaña al 503. "ok" acompaña al 200.

GET /version -> 200

    {"name": "wardline", "version": "<__version__>"}

GET /status -> 200

    {"app": "wardline", "version": "...", "environment": "local",
     "started_at": "<ISO-8601 UTC>",
     "components": {"http": "ok", "tcp": "ok", "udp": "ok", "database": "ok"},
     "bindings": {"http": "127.0.0.1:8080", "tcp": "127.0.0.1:9001",
                  "udp": "127.0.0.1:9002"}}

Los bindings reflejan el host y el puerto reales (en tests, el puerto efímero).

GET /metrics -> 200

    {"uptime_seconds": <float>,
     "http": {"requests_total": 0, "rate_limited_total": 0,
              "unauthorized_total": 0, "forbidden_total": 0},
     "tcp": {"connections_accepted": 0, "connections_rejected": 0,
             "connections_active": 0, "messages_valid": 0,
             "messages_invalid": 0, "bytes_in": 0, "timeouts": 0},
     "udp": {"datagrams_received": 0, "datagrams_valid": 0,
             "datagrams_dropped": 0, "bytes_in": 0},
     "security": {"events_total": 0, "alerts_open": 0,

Contadores monótonos desde el arranque del proceso, enteros >= 0.
uptime_seconds es float >= 0.

GET /events?limit=100&min_severity=&service=&simulation=
-> 200 {"events": [SecurityEvent, ...]} ordenados del más reciente al más antiguo.
limit por defecto 100, máximo 500.

GET /alerts?min_severity=LOW
-> 200 {"alerts": [SecurityEvent, ...]}
Una alerta es un SecurityEvent cuya severidad es >= min_severity y cuyo
event_type empieza por "anomaly_" o "security_". Los eventos puramente
informativos de ciclo de vida no son alertas.

GET /incidents -> 200 {"incidents": [Incident, ...]}
GET /incidents/{id} -> 200 Incident, o 404 not_found.

Incident:

    {"id": "inc_<12 hex>",
     "state": "DETECTED",
     "title": "<corto>",
     "source": "<client_id o system>",
     "service": "tcp",
     "severity": "HIGH",
     "correlation_id": "<uuid>",
     "simulation": true,
     "created_at": "<ISO-8601>",
     "updated_at": "<ISO-8601>",
     "actions": [{"at": "...", "actor": "<client_id del admin o system>",
                  "action": "acknowledge|contain|resolve|rollback|block",
                  "from_state": "...", "to_state": "...", "detail": "..."}]}

Transiciones legales, y ninguna otra:

    acknowledge: DETECTED -> INVESTIGATING          (operator o admin)
    contain:     INVESTIGATING -> CONTAINED         (solo admin)
                 y aplica un bloqueo lógico del client_id de incident.source
                 durante block_ttl_seconds. Si source es "system", no bloquees
                 a nadie; registra la contención como lógica sobre el incidente.
    resolve:     CONTAINED -> RECOVERING            (solo admin)
                 ejecuta la verificación de salud local;
                 si pasa, RECOVERING -> RESOLVED y levanta el bloqueo lógico
                 asociado a ese incidente;
                 si no pasa, el estado queda RECOVERING y la respuesta es 409
                 invalid_state_transition, con details.health igual al cuerpo
                 de /health.
    resolve:     RECOVERING -> (reintenta la misma verificación)

Cualquier otra transición: 409 invalid_state_transition, estado sin cambios.
Incidente desconocido: 404 not_found.
Ruta administrativa sin credencial: 401 unauthorized.
Rol insuficiente: 403 forbidden. No reveles si el id existe cuando el rol
no llega ni a viewer; un viewer sí puede recibir 404.

POST /simulation/run  (operator o admin) cuerpo:

    {"scenario": "burst" | "invalid_messages" | "connection_pressure" | "udp_burst" | "all",
     "mode": "inprocess" | "loopback"}

mode ausente => settings.simulation_mode_default.
Respuesta 200:

    {"scenario": "...", "mode": "...", "refused": false,
     "events_recorded": <int>, "correlation_id": "..."}

Si mode es loopback y el host de destino configurado no es loopback: 400
simulation_refused y cero sockets abiertos.
Si scenario es desconocido: 400 validation_error.
Este endpoint no acepta un campo "target", "host" ni "port". El destino, si
el modo loopback se usa, es exclusivamente el propio servidor ya enlazado.
Ignorar o rechazar cualquier campo extra (rechazar, con validation_error).

POST /admin/config cuerpo: objeto JSON solo con claves de la lista blanca.
200 {"generation": <int>, "applied": {...}}
400 validation_error si hay una clave fuera de lista o un valor fuera de rango.
Guarda la foto anterior en ConfigHistory antes de aplicar.

POST /admin/recovery/rollback
200 {"generation": <int>, "restored": {...}}
409 invalid_state_transition si no hay foto anterior (no se puede cruzar
por debajo de la generación 0).

POST /admin/clients/{client_id}/block
cuerpo opcional {"ttl_seconds": <int dentro de 1..3600>}
200 {"client_id": "...", "blocked_until": "<ISO-8601>"}
El bloqueo es lógico, por client_id, dentro del proceso. No ejecuta iptables,
pf, firewalls, rutas del sistema ni sockets crudos.

POST /admin/clients/{client_id}/unblock
200 {"client_id": "...", "blocked": false}
404 not_found si ese client_id no está bloqueado.

GET /missions -> {"missions": [resumen sin el texto largo de explicación]}
GET /missions/{id} -> misión completa o 404.
POST /missions/{id}/check -> ejecuta el chequeo local de esa misión.

    200 {"mission_id": "...", "passed": true|false,
         "observations": ["..."], "explanation": "..."}

Protocolo TCP. Texto UTF-8, un objeto JSON por línea, separador \n.
Acepta y elimina un \r final. Buffer de lectura con tope
tcp_max_message_bytes. Si la línea lo supera, responde un error
message_too_large, cuenta el suceso y cierra. No acumules el resto.

Primer mensaje obligatorio:

    {"type": "hello", "client_id": "<id>", "token": "<api-key o ausente>"}

Antes del prompt 07, token puede faltar y el principal es viewer no autenticado,
siempre que client_id sea válido. Desde el prompt 07, token es obligatorio;
si falta o no es válido, error unauthorized y se cierra la conexión.

Respuesta:

    {"type": "welcome", "client_id": "...", "role": "viewer", "session_id": "<uuid>"}

Después, el cliente puede enviar:

    {"type": "ping", "request_id": "<1..64 chars [A-Za-z0-9_-]>"}
    {"type": "echo", "request_id": "...", "payload": "<string, máximo 256 caracteres>"}
    {"type": "status", "request_id": "..."}
    {"type": "bye"}

Respuestas:

    {"type": "pong", "request_id": "..."}
    {"type": "echo", "request_id": "...", "payload": "..."}
    {"type": "status", "request_id": "...", "session_id": "...", "role": "..."}
    {"type": "bye", "request_id": null}

Error de línea:

    {"type": "error", "code": "<ErrorCode>", "message": "...", "request_id": null | "..."}

Cierra la sesión después de: message_too_large, timeout, circuit_open,
client_blocked, unauthorized en el hello, bye, o al llegar a
tcp_max_errors_per_session errores de validación.
No cierres por un único invalid_message si el contador aún no llega al tope;
responde el error y sigue, salvo que el hello haya fallado (el hello fallido
siempre cierra).

Campos desconocidos en un mensaje conocido se ignoran, no se reflejan.
type fuera del conjunto permitido: invalid_message.
JSON que no sea un objeto: invalid_message.
payload de echo que no sea string, o de más de 256 caracteres: invalid_message.
echo devuelve el mismo payload, sin interpretarlo ni evaluarlo.
No hay tipo "exec", "shell", "admin", "forward" ni "proxy". No los añadas.

Límites TCP que el servidor aplica él mismo, aunque el prompt 11 los centralice:
- como máximo tcp_max_connections sesiones aceptadas a la vez; el exceso se
  acepta solo lo necesario para escribir connection_limit y cerrar, o se
  rechaza en el backlog si la plataforma no permite escribir. Cuenta
  connections_rejected. No dejes el socket colgado.
- timeout de lectura tcp_read_timeout_seconds por línea.
- timeout de inactividad tcp_idle_timeout_seconds sin un mensaje completo.
- Ante timeout: si todavía puedes escribir, envía error timeout y cierra.

Protocolo UDP. Un datagrama, un objeto JSON, como máximo udp_max_datagram_bytes.
El servidor enlaza solo a udp_host permitido.

Tipos:

    {"type": "beacon", "client_id": "...", "token": "...", "seq": <int >= 0>}
    {"type": "ping", "client_id": "...", "token": "...", "seq": <int >= 0>,
     "request_id": "..."}

seq es obligatorio, entero >= 0 y <= 1_000_000_000.
Respuesta, un datagrama pequeño (máximo 200 bytes) al peer:

    {"type": "beacon_ack", "client_id": "...", "seq": 1, "role": "viewer"}
    {"type": "pong", "request_id": "...", "seq": 1}

Datagrama mayor que el límite: se descarta, se incrementa datagrams_dropped y
bytes_in con el tamaño observado hasta el límite de lectura del socket, y NO
se responde. Esto evita amplificación. Documenta esa decisión en el código
con un comentario de una línea.

Datagrama inválido y pequeño: respuesta de error <= 200 bytes con
{"type":"error","code":"...","message":"..."}.
Si el client_id está bloqueado: un error client_blocked <= 200 bytes, o
descarte si no cabe una respuesta pequeña. Nunca una respuesta mayor que
200 bytes.

Origen que no sea loopback (no debería ocurrir si el bind es correcto):
descarta en silencio, cuenta datagrams_dropped, registra un SecurityEvent
security_nonlocal_peer con severidad HIGH y simulation false. No respondas.

Desde el prompt 07, token es obligatorio también en UDP.

Anti-amplificación, regla permanente:
la respuesta UDP es siempre un JSON de como máximo 200 bytes.
No reflejes payload del cliente en UDP. UDP no tiene tipo echo.

Rate limiting. Token bucket por clave, reloj inyectable.

Claves:
- HTTP: principal.client_id si está autenticado; si no, "anon:" + ip
- TCP: client_id de la sesión, después del hello. El propio hello consume 1.
- UDP: client_id del datagrama válido. Los datagramas inválidos consumen
  la clave "invalid:" + ip, con el mismo bucket, para que un flujo de basura
  también tenga techo.

HTTP agotado: 429, cuerpo de error rate_limited, cabecera Retry-After en segundos
enteros >= 1.
TCP agotado: error rate_limited, no cierres por el primer exceso; cuenta como
error de sesión.
UDP agotado: descarta y cuenta. No respondas (no amplifiques un flood).
Cada rechazo genera un SecurityEvent event_type "security_rate_limited",
severity LOW, simulation false, salvo que el disparador sea el motor de
simulación, en cuyo caso simulation true y event_type "simulated_rate_abuse"
lo emite el simulador, no el limitador. El limitador sigue emitiendo
security_rate_limited cuando de verdad descarta.

Implementación del bucket: capacidad = rate_limit_burst, relleno
rate_limit_requests_per_minute / 60.0 tokens por segundo. No uses sleep para
aplicar el límite. Rechaza y sigue.

Cuotas: además del bucket, un contador por client_id de mensajes aceptados.
Al superar quota_events_per_client, error quota_exceeded. La cuota es un
contador del proceso, no un sistema de facturación.

Circuit breaker, uno por ServiceName TCP y otro por UDP, más uno HTTP.
Se abre cuando hay circuit_failure_threshold rechazos locales (validación,
tamaño, rate limit, timeout) dentro de circuit_window_seconds.
Abierto: las nuevas operaciones de ese servicio reciben circuit_open durante
circuit_open_seconds y no se ejecuta el trabajo. TCP cierra tras el error.
UDP descarta. HTTP responde 503 con code circuit_open.
Después pasa a half-open y deja pasar una sola operación de prueba.
No llama a sistemas externos. No es un proxy.

Backpressure: si connections_active == tcp_max_connections, se rechaza.
Si el tamaño de la cola interna de eventos de auditoría supera 1000, se
fusionan los siguientes en un solo evento event_type "security_log_volume",
severity HIGH, en lugar de escribir una línea por evento. La fusión es la
protección ante log flooding. No desactives la auditoría para "resolverlo".

Bloqueos: BlockRegistry.block(client_id, *, until, reason, incident_id) -> None
is_blocked(client_id, now) -> bool
unblock(client_id) -> bool
Un bloqueo vencido se trata como no bloqueado. No bloquees direcciones IP.
No hay API para bloquear 127.0.0.1. Un client_id bloqueado recibe
client_blocked en HTTP (403), TCP (error y cierre) y UDP (error corto o drop).

Simulación. Módulo wardline.simulation.

    def assert_loopback(host: str) -> None
        # levanta SimulationRefused si host no está en {127.0.0.1, localhost, ::1}

    class SimulationResult (frozen):
        scenario: str
        mode: Literal["inprocess", "loopback"]
        events: tuple[SecurityEvent, ...]
        refused: bool
        reason: str | None

    def simulate_burst(state, *, mode) -> SimulationResult
    def simulate_invalid_messages(state, *, mode) -> SimulationResult
    def simulate_connection_pressure(state, *, mode) -> SimulationResult
    def simulate_udp_burst(state, *, mode) -> SimulationResult
    def simulate_all(state, *, mode) -> list[SimulationResult]

Modo inprocess, el predeterminado:
no abre sockets. Construye SecurityEvent con simulation=true y los guarda
en el repositorio de eventos. Como máximo simulation_max_events por llamada.

Eventos sintéticos exactos:

    simulate_burst:
        event_type = "simulated_rate_abuse"
        service = http
        severity = MEDIUM
        source = "training-client"
        action = "recorded"

    simulate_invalid_messages:
        event_type = "simulated_invalid_input"
        service = tcp
        severity = LOW
        source = "training-client"
        action = "recorded"

    simulate_connection_pressure:
        event_type = "simulated_connection_pressure"
        service = tcp
        severity = HIGH
        source = "training-client"
        action = "recorded"

    simulate_udp_burst:
        event_type = "simulated_udp_burst"
        service = udp
        severity = MEDIUM
        source = "training-client"
        action = "recorded"

details debe incluir {"synthetic": true} y no incluir destinos de red.

Modo loopback, opcional y acotado:
solo si el servidor propio está enlazado a loopback. Presupuesto duro, no
configurable por el cliente HTTP:

    burst: como máximo 30 peticiones GET /health a 127.0.0.1, en <= 2 s,
           concurrencia <= 4. /health es público y barato.
    invalid_messages: como máximo 8 líneas no JSON al TCP propio, luego cierra.
    connection_pressure: como máximo 8 conexiones TCP al puerto propio,
           cada una envía hello válido y bye, luego cierra. Presupuesto de
           tiempo 2 s. No supera simulation_loopback_max_connections.
    udp_burst: como máximo 20 datagramas de <= 200 bytes al UDP propio.

Si el presupuesto se agota, paras, aunque el escenario no haya "terminado".
Si alguien intenta pasar un host distinto, refused=true, reason
"non_loopback_target", cero sockets, un evento security_simulation_refused
severity HIGH simulation true.
El modo loopback existe para observar los controles del propio proceso.
No es un generador de carga genérico: no acepta URL arbitraria, no acepta
número de hilos del usuario, no acepta duración del usuario.

Detección de anomalías (funciones puras sobre ventanas de eventos ya
estructurados; no inspeccionan payloads en busca de exploits; no ejecutan
contenido):

    Ventana por defecto: 30 segundos, reloj inyectado.

    - >= 5 eventos security_rate_limited o simulated_rate_abuse
      con el mismo source en la ventana
      -> anomaly_rate_abuse, MEDIUM

    - >= 10 eventos con event_type que contenga "invalid" y el mismo source
      -> anomaly_malformed_input, LOW

    - >= 5 connection_limit o simulated_connection_pressure del mismo source
      -> anomaly_connection_pressure, HIGH

    - >= 10 simulated_udp_burst o datagramas_dropped atribuidos al mismo source
      en la ventana
      -> anomaly_udp_burst, MEDIUM

    - un security_log_volume
      -> anomaly_log_volume, HIGH

Cada anomalía es un SecurityEvent con action "detected".
Si la severidad es >= anomaly_incident_min_severity (HIGH por defecto) y no
hay un incidente no resuelto con el mismo (source, event_type), se abre un
Incident en estado DETECTED. MEDIUM y menor solo quedan como alerta.

Correlación: el correlation_id del evento que cruzó el umbral se copia al
incidente. Si varios eventos cruzan a la vez, usa el del más reciente.

Verificación de salud para recuperación (solo loopback):

OBJETIVO

REGLAS DE SEGURIDAD

anidado se rechaza, excepto details que el cliente no envía. Los mensajes de
cliente no llevan objetos anidados. arrays se rechazan.

descompresor.

================================================================================
COMANDOS DE INSTALACIÓN
================================================================================

Hace falta Python 3.12 o superior ya instalado en la máquina. El laboratorio
no lo descarga.

    git clone <url-del-repositorio>
    cd wardline
    ./scripts/setup.sh

Equivalente manual, si los scripts todavía no existen a mitad de campaña:

    python3.12 -m venv .venv
    . .venv/bin/activate
    python -m pip install --upgrade pip
    python -m pip install -e ".[dev]"
    cp .env.example .env
    mkdir -p data/logs

Activar el entorno en una sesión nueva:

    . .venv/bin/activate


================================================================================
COMANDOS DE EJECUCIÓN
================================================================================

Arranque normal, solo loopback:

    ./scripts/run.sh

Equivalente:

    . .venv/bin/activate
    python -m wardline

Comprobar la configuración sin abrir sockets:

    WARDLINE_DRY_RUN=1 python -m wardline

Un solo servicio:

    python -m wardline --only http
    python -m wardline --only tcp
    python -m wardline --only udp

Sondas locales, con la clave ficticia de viewer:

    curl -sS http://127.0.0.1:8080/health
    curl -sS http://127.0.0.1:8080/version
    curl -sS -H "Authorization: Bearer dev-viewer-key" http://127.0.0.1:8080/status

Parar el proceso: Ctrl-C en el terminal donde corre. No hay ruta HTTP de apagado.

Con Docker, cuando el fichero compose ya exista, publicado solo en loopback
del anfitrión:

    docker compose up --build

La variable WARDLINE_CONTAINER=1 la pone el propio compose. No pongas
0.0.0.0 en los puertos publicados.


================================================================================
COMANDOS DE TESTING
================================================================================

Suite completa, con lint y tipos:

    ./scripts/test.sh

Equivalente:

    . .venv/bin/activate
    ruff check src tests
    mypy src
    pytest -q

Por capas:

    pytest -q tests/unit
    pytest -q tests/integration
    pytest -q tests/security

Con cobertura, el mismo umbral que CI:

    pytest -q --cov=wardline --cov-fail-under=70

Un archivo concreto, cuando un prompt está a medias:

    pytest -q tests/unit/test_contracts.py

Los tests no necesitan red externa y no deben ejecutarse contra un host que
no sea 127.0.0.1.


================================================================================
COMANDOS DE SIMULACIÓN
================================================================================

Modo por defecto, solo eventos internos, sin sockets:

    ./scripts/simulate.sh

Equivalente:

    . .venv/bin/activate
    python -m wardline.simulation --scenario all --mode inprocess

Un escenario concreto:

    python -m wardline.simulation --scenario burst --mode inprocess
    python -m wardline.simulation --scenario invalid_messages --mode inprocess
    python -m wardline.simulation --scenario connection_pressure --mode inprocess
    python -m wardline.simulation --scenario udp_burst --mode inprocess

Por la API, con los servicios ya arrancados y la clave ficticia de operator:

    curl -sS -X POST http://127.0.0.1:8080/simulation/run \
      -H "Authorization: Bearer dev-operator-key" \
      -H "Content-Type: application/json" \
      -d '{"scenario":"all","mode":"inprocess"}'

El modo loopback es opcional y solo habla con el propio servidor ya enlazado
en 127.0.0.1. No admite un host de destino:

    python -m wardline.simulation --scenario burst --mode loopback

Si los servicios no están en marcha, ese comando sale con código 2.
Si alguien añade un destino que no es loopback, el motor se niega y no abre
el socket.

Restablecer datos locales generados, sin tocar código ni .env:

    ./scripts/reset.sh

Ver los eventos sintéticos después de una simulación:

    curl -sS -H "Authorization: Bearer dev-viewer-key" \
      "http://127.0.0.1:8080/events?simulation=true"

Ejecutar los chequeos de las misiones con la clave ficticia de operator:

    curl -sS -X POST http://127.0.0.1:8080/missions/m01/check \
      -H "Authorization: Bearer dev-operator-key"

Sustituye m01 por m02, m03, m04 o m05. El alumno viewer puede leer la misión
pero no lanzar el chequeo.
